### `F21-1` — 세 결정이 겹치는 자리에서 앞의 둘을 안 셌다

`_stranded_rows` 가 `LIMIT ?` 로 읽은 뒤 `_view` 가 터진 row 를 조용히 버린다. 그 skip 은
`D-047` 이 넣었고 이유는 round 15 `F-2`(손상 row 하나가 목록 전체를 없앴다)다. **그래서 SQL
이 가져온 개수와 반환 개수가 다르다.** `D-050` 은 "`limit + 1` 개가 오면 잘린 것" 을
전제로 삼으며 앞의 둘을 안 셌다.

```text
후보 200 / 손상 1 / --limit 100
  전   출력 100줄 + UNREADABLE 1,  잘림 표시 없음   ← 후보 99개가 숨었다
  후   출력 100줄 + UNREADABLE 1 + 잘림 표시
```

`D-057` 이 `D-049` 의 이동을 `stranded()` 에도 적용했다. `SQL LIMIT` 을 버리고 **읽을 수
있는 row 를 `limit` 개 모으면 멈춘다.** `cli.py` 의 실행 코드는 안 바꿨다 — 판정식의
전제가 참이 되므로 고칠 것이 없다. signature 와 반환 타입도 그대로다.

**비용 주장을 실측으로 받쳤다.** `governance_ingress_commands` 에 정렬을 받쳐 줄 index 가
없어(`sqlite_autoindex_*` 셋뿐, `CREATE INDEX` 0건) `ORDER BY` 가 이미 전수 정렬을 강제한다.
`EXPLAIN QUERY PLAN` 이 `LIMIT` 유무와 무관하게 같다.

`F21-2` 는 **부수 효과로 구조적으로 닫혔다.** `limit + 1` 이 sqlite3 binding 에 도착하지
않는다 — `--limit 9223372036854775807` 이 수정 전 exit 1 / `OverflowError`, 수정 후 exit 0.
