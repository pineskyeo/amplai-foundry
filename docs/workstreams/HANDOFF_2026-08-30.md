## 새 세션이 반드시 읽을 것 넷

**CI 는 여전히 죽어 있고 사용자가 무시하기로 했다.** 계정 GitHub Actions 가 결제 문제로
멈춰 `steps=0` 으로 4초 만에 죽는다. **이번 세션의 PR 여덟은 전부 CI 없이 admin merge 했다.**
모든 근거는 로컬 실행이다. `PR #2` 의 41 commit 부채도 그대로다.

**주 체크아웃에서 `git checkout main` 이 안 된다.** synapse·cortex 둘 다 `main` 이 다른
worktree 에 물려 있다 (`.claude/worktrees/feat-retest`, `.claude/worktrees/gpm-connect`).
새 작업은 `main` 을 거치지 말고 `origin/main` 에서 바로 브랜치를 딴다.

```bash
git -C ~/workspace/<repo> fetch origin
git -C ~/workspace/<repo> switch -c feat/새작업 origin/main
```

**`--verify` 의 판정이 셋으로 늘었다.** `MATCH` / `LOCAL_NOT_ON_MAIN` / `MISMATCH` 다.
`rc` 를 여는 것은 `MISMATCH` 뿐이다. 봐주는 조건은 좁다 — 체크아웃이 default branch 밖에
있고 **동시에** `origin/<default>` 의 install record 가 그 kit 버전을 담을 때만이다.
`origin/main` 을 못 읽으면 그대로 `MISMATCH` 다.

**cortex 를 배포할 때 `[contract-ok]` 가 이제 필요 없다.** `PR #196` 이 그 원인을 닫았다.
다만 `docs/**/schemas/**` 와 `cortex.spec` 은 여전히 잡히므로, main 을 받아오는 병합처럼
그 경로가 딸려 오면 그때는 필요하다.

## fleet 배포 — `--project-home` 없이 한다

이번에 확립한 절차다. `install.py:935-936` 이 `--project-home` 없이는
`configure_project_store` 를 즉시 반환해 `store.register_app(..., repo_path=self.target)`
(`:953-955`) 이 안 불린다. **`ALR-007` 이 겪은 Store `repo_path` 덮어쓰기 사고의 원인이
정확히 그 줄이다.**

```bash
git -C ~/workspace/<app> worktree add --detach /tmp/kit-<app> origin/main
.venv/bin/python tools/amplai-loop-kit/install.py \
    --target /tmp/kit-<app> --app-id <app> --project-id ai-platform
# 그 저장소 방식으로 test → commit → PR → 머지 → worktree 제거
```

건너뛰는 것은 gitignore 된 `.ai-team/local/project.json` 하나뿐이라 **대상의 로컬 작업
사본을 동기화하거나 정리하지 않고 배포할 수 있다.**

**Store 바인딩이 필요하면 그것만 따로, 실제 체크아웃에서 한다** — worktree 나 임시 경로에서
`--project-home` 을 주면 `repo_path` 가 그 경로로 덮인다.

## 발견한 flaky test 하나 — 이 세션이 만든 것이 아니다

인계 문서를 쓰며 전체 pytest 를 한 번 더 돌리다 **한 번 실패했다.**

```text
FAILED tests/test_ingestion.py::test_concurrent_duplicate_ingestion_is_idempotent
  IngestionError: Source ID hash prefix 충돌이 발생했습니다
```

단독 3회, 전체 재실행 1회 모두 통과했다. **이 세션은 `tests/test_ingestion.py` 도
`src/amplai_foundry/ingestion/` 도 건드리지 않았다** — `git log b191edf..HEAD` 에 해당
경로 commit 이 없다.

성격은 이렇다. 그 test 는 **같은 내용을 thread 둘로 동시에 ingest** 하고 결과가
`["created", "duplicate"]` 이기를 기대한다. `service.py:158-167` 의 충돌 guard 는 기존
source record 를 훑어 같은 `identifier` 가 있으면 `IngestionError` 를 낸다. **중복 판정과
그 guard 가 한 transaction 이 아니다.** 두 thread 가 중복 판정을 함께 통과한 뒤 하나가
guard 에 걸리면, 정상 중복이 "hash prefix 충돌" 로 튄다 — 실제 해시 충돌이 아닌데 그
메시지가 나온다. **(추정)** 정확한 interleaving 은 계측하지 않았다.

재현이 드물어 이번 세션 범위에서 다루지 않았다. **누가 이 메시지를 실제 해시 충돌로 읽고
디버깅에 들어가면 시간을 크게 버린다** — 그것이 이 항목을 남기는 이유다.
