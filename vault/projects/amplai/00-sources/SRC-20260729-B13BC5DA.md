## Assistant

결론
두 방향 모두 가능합니다. 다만 역할을 이렇게 분리해야 합니다.
Hermes = 메신저 기반 비서·접수창구·작업 조율자
AMPLAI = 프로젝트 상태·Proposal·승인·검증을 관장하는 통제 계층
Hermes가 AMPLAI 자체의 권한과 기억까지 소유하면 위험합니다. 반대로 Hermes를 AMPLAI를 호출하는 Client Partner로 두면 지금 구상과 매우 잘 맞습니다.

1. Hermes를 비서 에이전트로 두는 방향
Hermes는 현재 Slack·Telegram 등을 연결하는 Messaging Gateway, 지속 메모리, Skills, 일정 작업, 다중 프로필을 지원하므로 항상 켜져 있는 AMPLAI 비서 역할에 잘 맞습니다. 프로젝트별 프로필을 분리하면 설정·메모리·세션·Skills도 격리할 수 있습니다. Hermes Messaging, Hermes Profiles
예를 들어 사용자는 메신저에서 이렇게만 요청할 수 있습니다.

“AMPLAI Phase 1A 진행 상황 알려줘.”
“이 아이디어를 로드맵에 반영해줘.”
“Phase 1A 구현 시작해.”
“검증 실패 원인 요약해줘.”
“올라온 Proposal 보여줘.”
“승인된 변경을 적용해.”
하지만 내부적으로는 Hermes가 직접 판단하거나 Git을 수정하면 안 됩니다.
영역	담당
자연어 대화, 음성·파일 접수	Hermes
사용자 의도 구조화	Hermes
프로젝트 추정값 전달	Hermes
실제 프로젝트 확정	AMPLAI ProjectResolver
Proposal 생성·버전 관리	AMPLAI
승인 권한·정책·감사 기록	AMPLAI
코드 구현	Codex·Claude·GLM Worker
테스트·평가·리뷰	AMPLAI Eval/Governor
결과 알림·요약	Hermes
특히 두 가지 경계가 중요합니다.
Hermes Memory는 정본이 아니다
Hermes 문서에서도 Memory는 사실, Skill은 절차를 저장하는 구조입니다. 하지만 이것을 AMPLAI의 정식 프로젝트 지식으로 사용하면 Hermes의 기억과 Foundry의 MemoryObject가 충돌할 수 있습니다. Hermes Memory/Skills
따라서:

Hermes Memory: 말투, 알림 방식, 사용자 선호, 최근 대화 맥락
AMPLAI MemoryObject: 설계 원칙, 결정, 로드맵, Proposal, 검증 결과
Git/Project Pack: 실제 코드와 이동 가능한 프로젝트 정본
으로 나누는 것이 맞습니다.
Hermes는 AMPLAI API만 호출한다
Hermes에게 광범위한 shell/Git 권한을 주기보다 전용 Skill 또는 MCP/API를 줍니다.
예:

submit_intent()
get_project_status()
list_proposals()
get_proposal()
decide_proposal()
start_approved_job()
get_job_result()
Hermes는 이 계약만 사용하고, 실제 변경은 AMPLAI가 AuthorityContext, Project Manifest, Proposal 상태를 확인한 후 수행해야 합니다.
2. Slack·Telegram에서 Proposal UI 만들기
가능합니다. 오히려 Proposal 승인 UX와 아주 잘 맞습니다.
Slack
Slack은 Block Kit 메시지에 버튼·선택 메뉴·입력창을 넣을 수 있고, 사용자가 버튼을 누르면 Interaction Request URL로 구조화된 payload를 전송합니다. Slack Block Kit, Slack Interactivity
Hermes도 현재 Slack에서 위험 명령 승인과 선택형 질문을 Block Kit 버튼으로 표시합니다. 다만 AMPLAI Proposal이라는 업무 의미는 기본 기능이 아니므로, AMPLAI 전용 Proposal Card와 callback 처리를 추가해야 합니다. Hermes Slack

예시는 다음과 같습니다.

PRP-0042 · AMPLAI · Phase 1A
Project Identity에 MemoryRef(namespace, local_id)를 도입합니다.
변경: 8 files
테스트: 42 passed
위험도: Medium
기준 버전: a13d92f
Proposal digest: 9e31…

[상세 보기] [수정 요청]
[승인] [거절]

승인 후 메시지를 갱신합니다.
✅ 이정훈 승인 · 2026-07-28 09:14
적용 대기 중 · Job JOB-0182
Telegram
Telegram은 메시지 아래에 Inline Keyboard를 붙이고, 버튼 클릭을 callback_query로 받을 수 있습니다. 따라서 승인·거절·상세보기 버튼을 동일하게 구현할 수 있습니다. Telegram Bot API
다만 callback_data는 1~64바이트이므로 Proposal 전체 정보를 넣으면 안 됩니다. 짧은 일회성 토큰만 넣어야 합니다.

callback_data = act_7Kp2vN9q
서버가 이 토큰을 다음 정보로 해석합니다.
proposal_id: PRP-0042
proposal_version: 3
proposal_digest: 9e31...
action: approve
expires_at: ...
allowed_actor: telegram-user-123
반드시 들어가야 하는 강제 장치
버튼이 있다고 승인 시스템이 안전해지는 것은 아닙니다. AMPLAI 서버가 다음을 강제해야 합니다.
Actor 검증
Slack/Telegram 사용자를 AMPLAI의 승인 주체와 매핑합니다.
Project 검증
버튼이 연결된 (namespace, proposal_id)를 다시 확인합니다.
버전과 Digest 검증
화면에 표시한 Proposal이 클릭 전에 변경됐다면 승인을 거부합니다.
상태 전이 검증
validated → approved → applied 같은 허용된 전이만 받습니다.
중복 클릭 방지
동일 callback을 여러 번 받아도 한 번만 처리합니다.
만료 처리
오래된 메시지의 버튼은 승인할 수 없게 합니다.
감사 기록
누가, 언제, 어느 채널에서, 어떤 버전을 승인했는지 보존합니다.
승인과 적용 분리
위험한 작업은 승인 후 별도의 적용 단계로 둡니다. 저위험 작업만 정책에 따라 승인 즉시 적용할 수 있습니다.
권장 구현 위치
현재 로드맵을 흔들면서 별도 Phase를 만들 필요는 없습니다.
Phase 1A: ProjectRef, ActorRef, AuthorityContext 확정
Phase 1B: 메신저 입력을 IntentRequest로 변환하고 Proposal 생성
Phase 1C: Hermes Skill·Messenger Adapter를 Project Pack에 포함
이후 Harness/Eval 단계: 승인 정책, 실행 격리, 자동 검증 강화
지금은 Phase 1A 계약을 먼저 확정하되, Slack 또는 Telegram의 읽기 전용 상태 조회 + Proposal 카드 시제품은 병행해도 됩니다. 실제 승인·적용은 Phase 1A의 프로젝트 식별과 권한 계약이 들어간 뒤 연결하는 것이 맞습니다.
Slack과 Telegram 중 추천
개인 AMPLAI 개발 시제품: Telegram이 설치와 실험이 간단
팀 협업·스레드·감사·기업 계정 관리: Slack이 더 적합
사내 기밀 코드·설계: 회사 승인 메신저를 우선하고, Telegram에는 Proposal 요약과 식별자만 표시
최종적으로는 채널 종속 설계를 피하고 아래 하나의 계약을 두는 것이 좋습니다.
ProposalAction
- proposal_ref
- expected_version
- expected_digest
- action: approve | reject | request_changes | apply
- actor_ref
- channel_ref
- action_token
- occurred_at
Slack과 Telegram은 이 계약을 각자의 버튼 UI로 렌더링하기만 하면 됩니다.
한 문장으로 정리하면:

Hermes를 AMPLAI의 비서 겸 메신저 관문으로 두는 것은 좋은 방향이지만, 프로젝트 판별·Proposal·승인·적용의 권한은 반드시 AMPLAI가 가져야 합니다.
