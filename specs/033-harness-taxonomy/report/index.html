요약. 지금 모델들이 우리 과제 묶음보다 강하다. 개선안이 정말 나은지 확정하려면 칸마다 "가끔 맞히는" 과제가 16개 이상 필요한데, 실제로는 3–8개뿐이다. 과제를 더 어렵게 늘릴지(추천), 확정 기준을 낮출지를 정해야 개선안 실험과 야간 루프가 의미 있게 돈다. 나머지 셋은 그 뒤 순서와 설정에 관한 것이다.

  1. 과제 포화 (다음 단계를 막는 결정). 확정(focused) 단계는 칸마다 validation split 의 informative 과제(정답률 0.2–0.9)를 max(16, n_min)개 요구한다(IC-20, stages.confirmatory_tasks). 측정값은 opus 3, sonnet 4, codex high 8, codex medium 5개다. development 를 합쳐도 7–14개라 split 을 바꿔도 못 채운다. 그래서 제안 2건의 meta search 가 계획 단계에서 NO_INFORMATIVE_TASKS 로 멈췄다(trial 0).
    • A. 어려운 과제를 직접 추가 (추천). bench 앱 6개 영역에 어려운 과제를 더 쓰고, fairness 검사 → 새 corpus freeze → 재calibration(칸 4개 약 6.5시간, calibration 9 기준) 순서로 간다. 이미지와 파이프라인을 그대로 쓴다. 어느 칸에서 informative 가 될지는 돌려 봐야 안다.
    • B. Terminal-Bench 2.0 과제 채택. 설계의 원래 경로다(§10.5, 약 40개 목표). 과제마다 docker 이미지, 통과 검증(admission), 이미지별 자격 시험이 필요하다. VM 은 CPU 2·4 GiB 이고, TB2 test 실행 명령은 확인 필요(§14 Q7)다. 가장 오래 걸린다.
    • C. 확정 최소 과제 수를 낮춤 (추천하지 않음). IC-20 변경과 eval-10 이 필요하다. 16 은 margin 0.25·신뢰 0.95 에서 나온 최소치라, 낮추면 같은 판정의 근거가 약해진다.

Layers And How Each Decides

과제와 상황마다 유리한 하네스가 다르므로, 레이어마다 실행 중 그 자리에서 판단한다. 판단기는 dev 데이터로 맞춘 규칙표를 쓰고, 표본이 적으면 상위 묶음으로 당겨(partial pooling) 추정하며, 운영 goal 에서는 탐색하지 않는다.

레이어판단 시점고르는 것사전값(판단기 없을 때)평가 지표
L1 해석계획 직후진행 / 되묻기 / ask_first 로 한 번 더 계획질문이 있으면 되묻기모호 과제의 되묻기 정밀도·재현율
L2 구조계획 뒤실행 전략 10종 중 하나repair_loop최선 전략 대비 regret
L3 역할계획 뒤역할별 칸(모델×강도)router 순서역할 배정별 해결당 token
L4 컨텍스트dispatchenv bootstrap, memory notes, retrieval 켜고 끄기manifest 그대로성공률과 token
L5 에이전트 옵션dispatchdriver_options 버전없음성공, turn, token
L6 실패 시시도 실패 후피드백 재시도 / 새로 재시도 / 상위 칸 escalate / 중단attempt policy재시도당 회복률
L7 빠른 검사최종 검증 전없음 / quick checks없음절약한 시간 vs 잡은 실패
L8 한도계획 뒤limits 버전배포 예산예산 초과 vs 놓친 성공
L10 실험 운영매일 밤무엇을 얼마나 시험할지상시 승인 정책밤당 개선 후보 수, 비용

L9(실행 이미지)는 정의만 하고 이번 범위에서 뺐다. 판단 방식(특징, 추정기, 선택 규칙, 대체 규칙)과 judge 모델(none / LLM 칸 / Jev 연결부)도 버전 있는 부품이라 교체하고 비교할 수 있다. Jev 는 연결부만 있고, 설정 전에는 JUDGE_NOT_CONFIGURED 로 막힌다.

Evaluation

How A Change Is Judged

판정 클래스

  • improvement: 성공률이 의미 있게 오름 (superiority)
  • efficiency: 성공률은 같고 비용이 줄어듦
  • non_inferior: 나빠지지 않음 (margin 0.25, 신뢰 0.95, 과제 16개 이상 필요)
  • regression, tradeoff, inconclusive

같은 과제를 짝지어 비교하고(paired), Wilson 구간을 보수적으로 쓴다. 여러 밤에 걸친 누적 판정은 e-process 로 하고, α 는 사슬마다 고정이다.

Calibration 과 품질

  • 칸×과제마다 1회 실행하고, 칸끼리 엇갈리거나 경계인 과제만 최대 5회까지 반복한다.
  • 과제를 informative / saturated / unsolved / flaky 로 나눠, 차이를 보여 주는 과제로 실험한다.
  • 평가기 자체도 버전이 있다. 바꾸려면 Q-01–Q-15 시험을 다시 돌려 code digest 에 묶어야 하고, 사람만 승인한다(IC-25, IC-26).
  • 평가 품질 지표: 변별력, 포화, 채점 흔들림, 오염, dev–holdout 차이, 실제 결과와의 일치, 영역 분포, 판정당 비용.
