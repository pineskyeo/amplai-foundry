Operator

What Needs Your Decision

코드는 끝났고, 이제 실제로 성능이 오르는지를 보여 줄 차례다. 그 전에 운영자(사람)만 할 수 있는 결정 네 가지가 남아 있다.

  1. 파일럿 시작과 예산. 칸 4개 calibration, 그다음 3일 밤 동안 밤마다 약 150 trial. 승인 명령(calibrate, nightly approve, 단계 gate)은 운영자가 직접 실행한다. 사람 승인을 agent 가 대신 쓰지 않는 것이 이 설계의 원칙이다(IC-17).
  2. Legacy 제거 목록 승인. V1·V2 와 V3 미사용 부분. 사람이 정할 항목은 knowledge CLI·vault(D1), Slack/Hermes governance와 ops serve(D2·D3), Kit 2.x 배포 중단(D9)이다. 근거 목록은 specs/033-harness-taxonomy/legacy-inventory.md.
  3. IC-30: 밤에 새 제안을 스스로 screen 해도 되는가. 지금은 낮에 사람이 screen 한 제안만 밤이 돌린다. 추천은 class A 부품에 한해 기계적 screen(보호 영역 검사와 leak gate)을 허용하는 것이다. 보호 영역(class C) 권한이 바뀌므로 결정 전에는 구현하지 않았다.
  4. 잠정 결정 확인. IC-15–IC-29, IC-31, IC-32 는 추천안으로 잠정 구현됐다. 각각은 제약을 더하거나 내부 필드만 더한다. 야간 루프를 켜기 전에 확인이 필요하다(결정 기록).

Evaluation

How A Change Is Judged

판정 클래스

  • improvement: 성공률이 의미 있게 오름 (superiority)
  • efficiency: 성공률은 같고 비용이 줄어듦
  • non_inferior: 나빠지지 않음 (margin 0.25, 신뢰 0.95, 과제 16개 이상 필요)
  • regression, tradeoff, inconclusive

같은 과제를 짝지어 비교하고(paired), Wilson 구간을 보수적으로 쓴다. 여러 밤에 걸친 누적 판정은 e-process 로 하고, α 는 사슬마다 고정이다.

Calibration 과 품질

  • 칸×과제마다 1회 실행하고, 칸끼리 엇갈리거나 경계인 과제만 최대 5회까지 반복한다.
  • 과제를 informative / saturated / unsolved / flaky 로 나눠, 차이를 보여 주는 과제로 실험한다.
  • 평가기 자체도 버전이 있다. 바꾸려면 Q-01–Q-15 시험을 다시 돌려 code digest 에 묶어야 하고, 사람만 승인한다(IC-25, IC-26).
  • 평가 품질 지표: 변별력, 포화, 채점 흔들림, 오염, dev–holdout 차이, 실제 결과와의 일치, 영역 분포, 판정당 비용.
