# MGC-012-P5-T035 — Separate the recovery sweeps from the speculative claim

대상: round 17 `F17-1`(P1), `F17-2`(P1), `F17-7`(B-P2), `A17-1`, `A17-4`.
결정: `D-045`, `D-047`.

## The Root — 한 자리에서 셋이 나왔다

`_claim_one` 이 성격이 다른 두 작업을 **한 transaction** 에 묶고 있었다.

| 작업 | 성격 | 실패하면 |
|---|---|---|
| lease-expiry sweep, exhaustion sweep | **회수** | 되돌릴 이유가 없다. lease 는 정말 만료됐다 |
| SELECT + claim UPDATE | **투기** | 되돌아가야 한다 |

`_view` 가 손상 row 에서 `ValueError` 를 내면 `governance_transaction` 이 정상 rollback 하는데,
그것이 투기뿐 아니라 **회수까지 되돌린다.** 그래서 손상 row 의 durable state 가 `leased`+만료로
남고, `_dead_letter_unreadable` 의 `state IN ('pending','retry_wait')` guard 가 0행을 낸다.
`cleared` 판정으로 `claim_next` 가 닫히고 뒤 command 는 영원히 `pending` 이다 —
**round 15 `F-1` 의 head-of-line 차단이 되돌아온 것이다.**

## AC-04 — Guard 가 0행을 내는 State 전수

두 방법으로 셌다. **SQL rowcount 실측**과 **WHERE 절 독해**이고 둘이 같다.

| durable state | rowcount | 이 결과가 옳은가 |
|---|---|---|
| `pending` | 1 | 치운다 |
| `retry_wait` | 1 | 치운다 |
| `leased` | 0 | 옳다. 다른 worker 가 **살아 있는** lease 를 쥐고 있다 |
| `completed` | 0 | 옳다. 건드리면 `completed_at` CHECK 를 깬다 |
| `recovery_hold` | 0 | 옳다. operator 가 잡고 있다 |
| `dead_letter` | 0 | 옳다. 이미 치워졌다 |
| generation 불일치 | 0 | 옳다. 그 사이 다른 claim 이 있었다 |

`state` 여섯 중 통과는 둘, 0행은 넷. generation 불일치를 더하면 **0행을 내는 경우 다섯**이다.
round 17 이 "도달 경로 못 찾음" 으로 남긴 세 칸(`completed`, `recovery_hold`, generation
불일치)도 durable row 를 실제로 만들어 rowcount 를 관찰했다 — **guard 동작은 셋 다 확인했다.**
도달 경로 자체는 여전히 코드에서 특정하지 못했고 그 사실을 그대로 적는다.

전에는 `leased` 칸이 **틀렸다.** lease 가 만료된 `leased` 는 소유자가 없는데 guard 가 그것을
"다른 worker 가 가져갔다" 로 읽었다.

## The Change — Guard 를 넓히지 않고 닫는다

`_sweep_recoverable()` 을 새로 두고 `claim_next` 의 loop 안, `_claim_one` **앞**에서 부른다.
자기 transaction 으로 commit 한다.

- **`F17-7` 이 닫힌다.** 실패한 claim 이 남의 회수를 되돌리지 않는다.
- **`F17-1` 이 닫힌다.** 손상 row 가 `leased`+만료면 sweep 이 durable 하게 `retry_wait` 로
  바꾸므로 **기존 guard 가 맞는다.**

**guard 를 넓혀 고치지 않았다.** 넓히면 round 16 `FR-1` 이 막은 "살아 있는 lease 를 지운다" 가
되살아난다. 그 worker 는 governed decision 을 이미 commit 했을 수 있다.

`F17-2` 는 이것으로 안 닫힌다. `D-047` 이 정한 대로 `unreadable()` 의 조회 범위만
"읽을 수 없는 durable row" 로 넓혔다. **`stranded()` 의 계약과 CLI 출력 형식은 그대로다.**

## 새 구조가 요구한 것 — 다섯을 셌다

round 16 blocker 넷이 wave 9 의 새 구조 하나에서 나왔다. 이번에는 먼저 센다. manifest 는
넷을 예상했는데 **실측은 다섯**이었다.

| # | 요구 | 처리 |
|---|---|---|
| 1 | sweep 자체의 실패 | `sqlite3.Error` 를 그대로 올린다. `process_next` 가 `CLAIM_FAILED` 로 잡는다 — `_claim_one` 과 같다 |
| 2 | sweep 과 claim 사이의 경합 | 정상이다. claim 의 `claim_generation`+`state` guard 가 처리한다 |
| 3 | sweep 결과를 되돌릴 수 없게 됨 | 그것이 옳다. lease 는 정말 만료됐고 시도는 정말 소진됐다 |
| 4 | claim 실패 후에도 `INGRESS_LEASE_EXPIRED` 가 durable 하게 남음 | 옳다. 3과 같은 이유다 |
| 5 | **`connect()` 순서에 결합된 test 가 밀림** | **manifest 가 놓쳤다.** 아래 절 |

### 다섯째 — 실측으로 찾았고 실측으로 고쳤다

sweep 이 자기 connection 을 쓰므로 `validate()` 호출 순서가 바뀐다. filesystem-guard test 둘이
그 순서를 세어 창을 잡는다. 추정하지 않고 호출자를 찍어 실측했다.

```text
1-2  connect < _sweep_recoverable < claim_next < process_next   ← 새로 생긴 것
3-4  connect < _claim_one < claim_next < process_next
5-6  connect < process < process_next
7-8  connect < _finalize < complete < _transition
```

**정확히 2 만큼 밀렸다.** 두 test 의 창을 `(5,5)` → `(7,7)` 로 옮겼고 **때리는 지점은
그대로다** — 하나는 `_transition`, 다른 하나는 `committed_decision()` 의 첫 읽기다. 주석의
실측 표도 새 값으로 다시 적었다.

## AC-05 — 주석을 코드에 맞췄다

| id | 전에 적혀 있던 것 | 코드가 실제로 하는 것 |
|---|---|---|
| `A17-1` | "`generation` 은 이 claim 이 쓴 값(`+1`)" | SELECT 가 읽은 **claim 이전** 값이다. `+1` 을 쓰는 write 는 rollback 된다 |
| `A17-4` | "0행이라는 사실을 호출자에게 알려야 한다" | 이 함수는 rowcount 를 내지 않는다. 진행 판정은 `claim_next` 의 `cleared` set 이 한다 |

둘 다 결론은 맞고 전제가 틀렸다. 전제만 고쳤다.

## Out Of Scope — 실측했고 고치지 않았다

`OutboxDispatcher.claim_next`(`events.py:3025`)가 **같은 형태**다. sweep 둘이 claim
transaction 안에 있고 마지막 줄이 같은 transaction 안에서 `_get_in_connection` 으로 view 를
만든다(`:3150`). 그 안의 `_view_row`(`:3469`)는 `model_validate` 를 쓴다.

실측했다 — `payload_json` 을 손상시키고 `claim_next` 를 두 번 불렀다.

```text
claim #1 -> JSONDecodeError (raw 로 나간다)
  poison durable -> (pending, attempts=0)
claim #2 -> JSONDecodeError
  poison durable -> (pending, attempts=0)
```

ingress 의 round 15 `F-1` 과 같다. Outbox 는 `destination_sequence` 순서를 강제하므로 뒤
event 가 아예 안 뽑혀 차단이 더 강하다.

**도달 경로는 더 좁다.** `governance_outbox_payload_immutable` trigger(`migrations.py:2031`)가
정상 UPDATE 경로에서 payload 11 column 을 막는다. ingress 의 `channel_json` 에는 그 보호가
없다. 위 실측은 trigger 를 내려 `D-045` 가 전제하는 디스크 수준 손상을 흉내낸 것이다.

Outbox 에는 `_dead_letter_unreadable` 에 해당하는 치우기 경로가 **없다** — `D-045` 는 ingress
에만 적용됐다. 사용자가 2026-08-26 에 범위 밖으로 두기로 정했다. 고치지 않고 기록한다.
