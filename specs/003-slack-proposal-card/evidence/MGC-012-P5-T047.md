# MGC-012-P5-T047 — 반환 개수가 곧 발견 개수가 된다

round 21 의 `F21-1`(P1)과 `F21-2` 를 닫는다. `D-057` 이 정한 안 A 다.

## 뿌리 — 세 결정이 겹치는 자리

`_stranded_rows` 는 `LIMIT ?` 로 `limit` 개를 읽은 뒤 `_view` 가 터진 row 를 조용히
버린다. 그 skip 은 `D-047` 이 넣었고, 그것이 존재하는 이유는 round 15 `F-2`(손상 row
하나가 목록 전체를 없앴다)다. **그래서 SQL 이 가져온 개수와 반환 개수가 다르다.**

`D-050` 은 "`limit + 1` 을 요청해 `limit + 1` 개가 오면 잘린 것" 을 전제로 삼았다.
`unreadable()` 에서는 맞다 — 그 함수는 손상 row 만 모으므로 반환 개수 = 발견 개수다.
**`stranded()` 에서는 틀리다.** `D-050` 이 앞의 둘을 안 셌다.

## RED → GREEN — 실측

후보 200 (`dead_letter` 벽) / `--limit 100`. 창 앞의 row 를 손상시킨다.

| 손상 row | 수정 전 | 수정 후 |
|---|---|---|
| 0개 | 출력 100줄 + 잘림 표시 | 출력 100줄 + 잘림 표시 |
| 1개 | 출력 100줄 + `UNREADABLE` 1줄, **잘림 표시 없음** | 출력 100줄 + `UNREADABLE` 1줄 + 잘림 표시 |

```text
수정 전  {'exit': 0, 'lines': 101, 'unreadable': 1, 'truncation': False}   ← 숨은 후보 99개
수정 후  {'exit': 0, 'lines': 102, 'unreadable': 1, 'truncation': True}
```

`len(commands) > limit` 이 `100 > 100` 이라 거짓이었다. **`D-050` 이 없애려던 침묵
그 자체다** — 손상 row 가 있다는 것은 보이고, 목록이 잘렸다는 것은 안 보인다.

## 고침

`_stranded_rows` 가 `SQL LIMIT` 을 버리고 **읽을 수 있는 row 를 `limit` 개 모으면
멈춘다.** `unreadable()` 이 `D-049` 로 이미 쓰는 규칙과 같다.

```text
-  "ORDER BY received_at, command_id LIMIT ?",      +  "ORDER BY received_at, command_id",
-  (max_attempts, max_attempts, now, limit),        +  (max_attempts, max_attempts, now),
                                                    +  if len(readable) >= limit:
                                                    +      break
```

`cli.py` 의 **실행 코드는 한 줄도 안 고쳤다.** 판정식의 전제가 참이 되므로 고칠 것이
없다. 바뀐 것은 그 위 주석뿐이고 그것은 `T046` 이 소유한 정정이다.
signature 와 반환 타입도 안 바뀐다 — `D-047`·`D-048`·`D-049` 가 공통으로 건 불변이고
`D-050` 이 같은 이유로 이미 거절한 안이다.

## 비용 — 늘지 않는다

`governance_ingress_commands` 에 **이 정렬을 받쳐 줄 index 가 없다.** `sqlite_master` 에
그 표의 index 는 `sqlite_autoindex_governance_ingress_commands_1`~`_3` 셋뿐이고 전부
UNIQUE 제약이 만든 것이라 `received_at, command_id` 순서를 못 준다. 명시적으로 만든
`CREATE INDEX` 는 이 저장소 전체에서 그 표에 하나도 없다. 그래서 `ORDER BY received_at,
command_id` 가 이미 전수 정렬을 강제한다.

```text
stranded WITH LIMIT    SCAN governance_ingress_commands + USE TEMP B-TREE FOR ORDER BY
stranded NO LIMIT      SCAN governance_ingress_commands + USE TEMP B-TREE FOR ORDER BY
unreadable (현행)       SCAN governance_ingress_commands + USE TEMP B-TREE FOR ORDER BY
```

**세 계획이 같다.** `SQL LIMIT` 은 지금도 스캔을 줄이지 않았다. 늘어나는 것은 `_view`
호출뿐이고 그것도 `limit` 개를 채우면 멈춘다. 그리고 **같은 CLI 명령이 이미 `unreadable()`
로 더 넓은 스캔을 한 번 한다** — `D-049` 가 그 대가를 명시적으로 받아들였다. 이 변경이
더하는 비용은 그보다 작다.

## `F21-2` — 구조적으로 닫혔다

`--limit` 의 양쪽 끝을 전부 실측했다. wave 14 는 아래쪽 끝만 셌고 위쪽 끝이 `F21-2` 가
됐다.

| `--limit` | 수정 전 | 수정 후 |
|---|---|---|
| `0` | exit 1, `SystemExit` | exit 1, `SystemExit` |
| `-1` | exit 1, `SystemExit` | exit 1, `SystemExit` |
| `1` | exit 0 | exit 0 |
| `9223372036854775806` | exit 0 | exit 0 |
| `9223372036854775807` | **exit 1, `OverflowError`** | exit 0 |

`limit + 1 = 2**63` 이 sqlite3 binding 에 도착해 터졌고 CLI 의 `except` 사슬
(`GovernanceStoreError`·`GovernanceMigrationError`·`IngressError`·`ValueError`·
`sqlite3.Error`)에 그 예외가 없어 raw traceback 이 그대로 나갔다.

**`D-057` 이 `SQL LIMIT` 을 없애 binding 자체가 사라졌다.** guard 가 잡는 것이 아니라
도달 경로가 없어진 것이다 — 그 구분을 적는다. 되돌아오는 것은
`test_stranded_survives_a_limit_at_the_top_of_int64` 가 막는다.

**선언 단계 guard 는 둘 다 안 넣었고 이유가 다르다.**

`typer.Option(max=...)` 은 지금까지 받던 값을 거절하는 **새 계약**이 되고 그것을 정당화할
근거가 없다. overflow 는 이미 도달 경로가 없다.

`typer.Option(min=1)` 은 `A21-9` 가 두 라운드째 지적한 것이고 같은 파일 `:201`(`search`
command)이 실제로 쓴다. **넣으면 exit code 가 바뀐다** — typer 의 min 위반은 usage error 라
**exit 2** 이고, 지금 CLI guard 는 `_fatal` 로 **exit 1** 을 낸다. 직접 재현해 확인했다.
`test_stranded_still_rejects_a_non_positive_limit` 이 `exit_code == 1` 을 못박고 있고 그것은
wave 14 가 round 20 `F20-1` 의 부작용을 막으려고 세운 계약이다. **exit code 를 바꾸는 것은
public contract 변경이라 Decision 이 필요하다** — 이 wave 의 범위 밖이다. `A21-9` 는 열린
Advisory 로 남는다.
