## AC-01 / AC-02 — `N18-1` (P1)

`D-048` 대로 `unreadable()` 의 SELECT 에 `WHERE state != 'completed'` 를 넣었다.

**RED (고침 전)**

```text
전체 152 row, poison 앞에 150 개
unreadable(limit=100) -> ()
unreadable(limit=200) -> ('CMD-A954E3FC6E1453AA',)
```

**GREEN (고침 후)**

```text
전체 152 row, poison 앞에 150 개
unreadable(limit=100) -> ('CMD-0715512877422D4A',)
unreadable(limit=200) -> ('CMD-0715512877422D4A',)
```

`limit` 이 **후보 상한**으로 돌아왔다. `stranded()` 와 같은 규칙이다.

> **정정 (wave 14 / `T045`, round 20 `C20-1`).** **이 문장은 틀렸다.** `D-048` 의 `Amended`
> 각주와 `D-049` 의 `Amends` 절이 한 글자까지 같은 이 문장을 지목한다 — 두 후보 집합이
> 실제로 다르고, `SQL LIMIT` 을 쓰는 한 어떤 state 집합을 골라도 창 안의 읽을 수 있는 row 가
> 손상 row 를 민다 (round 19 `F19-1`). `D-049` 가 `LIMIT` 을 python 출력 상한으로 옮겼고,
> **`limit` 의 뜻이 `stranded()` 와 다르다는 사실은 없앨 수 없는 차이**로 남았다.
>
> 위 표의 `limit` 의 의미 행("wave 12: `stranded()` 와 같게")도 같은 이유로 틀렸다.
>
> **본문은 지우지 않는다** — wave 12 가 무엇을 근거로 설계했는지가 기록이다. wave 13 이
> 같은 파일의 다른 자리(`R19-3`)에는 각주를 달고 이 자리에는 안 달아서 round 20 이
> **선택적 누락**으로 잡았다.

## AC-03 — `N18-2`

`_sweep_recoverable` 의 첫째 UPDATE 가 `retry_at = now` 를 쓰므로 **같은 transaction
안에서** 둘째 UPDATE 의 `retry_at <= now` 가 참이 된다. `leased`+만료+`attempts >= max` 인
row 는 거기서 바로 `dead_letter` 로 가고 `_dead_letter_unreadable` 에 **도달하지 않는다.**

실측이다.

```text
claim_next     -> CMD-AACFB69C21A183FD   (뒤 command 를 claim 한다 — 큐는 안 막힌다)
poison durable -> ('dead_letter', 5, 'INGRESS_LEASE_EXPIRED')
unreadable()   -> ('CMD-A5667FAD9AD2A845',)
```

`last_error_code` 가 `INGRESS_COMMAND_UNREADABLE` 이 아니다. **둘 다 사실이다** — lease 가
만료됐고 시도가 소진됐다. 읽을 수 없다는 것은 아직 발견되지 않았을 뿐이다. `D-045` 의
`INGRESS_COMMAND_UNREADABLE` 은 `_dead_letter_unreadable` 이 치운 경로의 표시다.

**중요한 것은 회수 경로가 살아 있다는 것이다.** `dead_letter` 는 `unreadable()` 의 후보라
operator 가 그 row 를 본다.

`ingress.py` 의 state 표와 `_sweep_recoverable` docstring 에 이 경로를 적었다. **표가 그
경로를 안 담은 것이 결함이었다.**

## AC-04 — `F18-R1`

기존 `..._filesystem_failure_in_claim_next_...` 는 `window=(1, 10**6)` 으로 store 를 통째로
막는다. sweep 이 실패를 삼켜도 뒤이은 `_claim_one` 이 대신 실패해 `CLAIM_FAILED` 가 나온다
— **그 test 는 이 지점을 가르지 못한다.**

새 test 는 **sweep 의 connect 하나만** 막는다 (`window=(1, 1)`). wave 11 이 실측한
`validate()` 순서에서 1-2 가 `_sweep_recoverable`, 3-4 가 `_claim_one` 이다.

## Mutation — 셋을 실제로 넣고 되돌렸다

**`.pyc` 캐시를 막고 돌렸다** (round 18 `A18-R1`). `PYTHONDONTWRITEBYTECODE=1` 을 주고
`__pycache__` 를 먼저 지웠다.

| # | mutation | 판정 | 죽은 test |
|---|---|---|---|
| M11 | `unreadable()` 의 `WHERE state != 'completed'` 제거 | **KILLED** | `..._stays_visible_behind_a_wall_of_completed_ones` (1건) |
| M12 | sweep 호출을 `try/except: pass` 로 감쌈 | **KILLED** | `..._a_sweep_failure_alone_still_closes_the_claim` (1건) |
| M13 | `unreadable()` 의 `limit < 1` guard 제거 | **KILLED** | `..._unreadable_rejects_a_non_positive_limit` (1건) |

셋이 **서로 다른 test** 를 죽인다.

M12 의 실패 메시지가 review 지적을 그대로 보여준다.

```text
E  assert <WorkerOutcome.COMPLETED: 'completed'> is <WorkerOutcome.CLAIM_FAILED: 'claim_failed'>
FAILED ... test_a_sweep_failure_alone_still_closes_the_claim
   - AssertionError: sweep 실패를 삼키면 claim 이 그대로 진행돼 만료 lease 회수...
```

sweep 실패를 삼키면 claim 이 **성공**해서 `COMPLETED` 가 된다. 만료 lease 회수가 조용히
사라지는 경로다.
