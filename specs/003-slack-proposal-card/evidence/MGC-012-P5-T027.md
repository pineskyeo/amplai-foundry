## The Change

`claim_next` 를 두 겹으로 나눴다.

```python
while True:
    try:
        return self._claim_one(worker_id)
    except _UnreadableCommand as unreadable:
        self._dead_letter_unreadable(unreadable.command_id)
```

`_claim_one` 안에서 `_view` 가 실패하면 `_UnreadableCommand` 를 올린다. **치우는 write 는
claim transaction 밖이다** — 안에서 하면 그 transaction 의 rollback 이 치우기까지 되돌린다.
`governance_transaction` 이 그 예외로 정상 rollback 하고, `claim_next` 가 밖에서 새
transaction 으로 `dead_letter` + `INGRESS_COMMAND_UNREADABLE` 을 쓴 뒤 loop 를 돈다.

손상이 둘 이상이어도 한 번의 `claim_next` 호출로 전부 치우고 건강한 row 에 도달한다. 한 번에
하나만 치우고 반환하면 worker loop 가 손상 수만큼 헛돌고, 그동안 큐는 여전히 막힌 것으로
보인다.

## Why The Exception Set Is Narrow

`_UNREADABLE_ROW = (ValueError,)` 다.

- `json.JSONDecodeError` 와 pydantic `ValidationError` 둘 다 `ValueError` 의 subclass 다.
- `IndexError`(`row[N]` 범위)와 `TypeError` 는 **넣지 않았다.** 그것은 데이터 손상이 아니라
  구현 결함이다. 넣으면 오타 하나가 durable dead letter 로 조용히 숨는다.
- `Exception` 으로 넓히지 않는다. 같은 이유다.

## AC-06 — Why The Unreadable Row Is Not In The List

manifest 의 AC-06 초안은 "손상 row 가 목록에 있고" 였다. **이 설계로는 만족할 수 없어
착수 전에 고쳤다** (manifest 에 정정 기록).

> **표현 정정 (round 16).** 처음 "구현 불가능하다" 로 적었는데 과장이다. `stranded()` 의
> 반환 model 을 바꾸면 가능했다 — 불가능한 것이 아니라 그 설계를 택하지 않은 것이다.
> 그리고 "구현 전" 이라는 시점 주장은 manifest 가 untracked 라 저장소에서 검증할 수 없다. `stranded()` 는 `tuple[IngressCommandView, ...]` 를 내는데
손상 row 는 그 model 로 만들 수 없다 — 그게 손상의 정의다. 빈 값을 채운 가짜 view 는
operator 에게 거짓을 보이는 것이라 더 나쁘다.

그래서 `unreadable()` 이 `command_id` 만 낸다. CLI 가 둘을 함께 보인다.

**구현 뒤에 AC 를 맞추지 않았다.** round 12 `C-2` 가 잡은 것이 그 순서였다.
