## What Was Wrong

`_finalize`(`:323`)가 `_settle_exhausted_retry` 를 `:332` 에서 부르는데 그 호출이 `try:`
**밖**이었다. 그 안 `:444` 가 `committed_decision()` 을 부르고, 그것이 `ingress.get()` 과
`decisions.result_for()` 로 connection 두 개를 새로 연다. `_finalize` 의 다른 store 호출은
전부 감싸져 있었다 — **이 읽기 하나만 무방비였다.**

**실패 모드가 상관돼 있다.** 재시도를 소진시킨 그 조건(store busy)이 이 읽기도 실패시킨다.

## AC-09 — What A Busy Store Actually Raises

가정하지 않고 쟀다.

| 만든 조건 | 올라온 예외 | `(GovernanceStoreError, IngressError, sqlite3.Error)` 에 잡히는가 |
|---|---|---|
| 다른 connection 이 `BEGIN EXCLUSIVE` | **예외 없음** | — |
| db 디렉터리 제거 | `sqlite3.OperationalError` | **예** |
| db 파일 손상 | 예외 없음 | — |

**쓰기 lock 은 읽기를 막지 못한다.** store 가 WAL 모드라 그렇다. 이것은 round 13 이 적은
"OperationalError database is locked" 가 이 읽기에서 자연 발생한 것이 아니라 주입된
것이었음을 뜻한다. 그래도 **결함 자체는 실재한다** — 위 재현이 보인다. 실패 원인이 무엇이든
그 예외는 `process_next` 밖으로 나갔다.

실측된 type 은 잡는 집합 안이다. `except Exception` 으로 넓히지 않았다 — 넓히면 프로그래밍
오류까지 침묵이 되어 결함이 durable 하게 숨는다.

## The Fix (D-042)

```python
try:
    committed = self.committed_decision(claim.command_id)
except (GovernanceStoreError, IngressError, sqlite3.Error):
    return WorkerOutcome.RECOVERY_HOLD, _DECISION_COMMITTED_UNRECONCILED
if committed is not None:
    return WorkerOutcome.RECOVERY_HOLD, _DECISION_COMMITTED_UNRECONCILED
return WorkerOutcome.RECOVERY_HOLD, error_code
```

읽기가 실패하면 **결정이 기록됐을 수 있다는 보수적 가정**으로 침묵한다. 모르는 상태에서
`unavailable` 을 보내면 이미 배달된 Result Card 와 모순될 수 있고 그 통지는 되돌릴 수 없다.
침묵은 `stranded()` 로 회수할 수 있다. **되돌릴 수 있는 쪽을 고른다.**

`D-042` 가 기각한 최소 변경안(`_finalize` 의 기존 `try` 안으로 호출만 옮기기)은 쓰지 않았다.
그러면 승격 자체가 일어나지 않아 command 가 lease 만료 → `dead_letter` 로 가고, round 11
`R-3` 이 닫으려던 영구 침묵이 일부 복귀한다.

## F-3 — Why Feedback Could Not Catch It

`_settle_exhausted_retry` 의 마지막 `return ..., error_code` 를 `..., None` 으로 바꿔도 전
suite 가 통과했다. `_transition` 이 `code = error_code or "INGRESS_DECISION_FAILED"` 를 쓰므로
durable `last_error_code` 가 조용히 generic 이 된다.

**통지로는 이것을 볼 수 없다.** `_safe_outcome` 은 mapping 되지 않은 code 와 `None` 을
똑같이 `unavailable` 로 처리한다. durable 값을 직접 봐야 한다. 새 test 가 `ingress.get()` 과
`stranded()` 둘 다에서 `INGRESS_DECISION_UNAVAILABLE` 을 확인한다.

round 12 evidence 의 "`R-2` 의 주 경로 — 원인 code 가 살아남는다" 를 round 13 이 반증했고,
이제 test 가 그것을 붙잡는다.

## PBC-3 — Round 13 Was Wrong. The Test Was Not Empty.

round 13 은 `test_a_first_successful_decision_sends_no_safe_feedback` 을 "docstring 에 대해
동어반복" 으로 판정하고 삭제를 지시했다. **지우지 않았다.** 성분을 하나씩 갈라 재면 이렇게
나뉜다.

| 지운 성분 | 죽는 test |
|---|---|
| `result.outcome is WorkerOutcome.COMPLETED` | **없었다 — 무방비** |
| `result.decision is not None` | 문제의 그 test **만** |
| `result.decision.replayed` | `test_a_real_first_successful_decision_sends_no_feedback` **만** |

두 test 는 같은 `if` 의 **다른 성분**을 잡는다. 지웠다면 `result.decision is not None` 이
무방비가 되고, `decision` 없는 완료 결과에서 `None.replayed` 로 `AttributeError` 가 나
worker 가 죽는다.

round 13 의 판정이 틀린 이유는 그 test 의 **이름**이 replay 조건을 잡는 것처럼 읽혔기
때문이다. 이름과 docstring 을 실제로 잡는 것에 맞게 고쳤다 —
`test_a_completed_result_without_a_decision_sends_no_safe_feedback`.

그리고 **세 번째 성분은 아무도 잡지 않았다.** round 13 도 이것을 세지 않았다. 지우면 replay
된 결정을 실은 recovery hold 가 `already_completed` 로 보고되어 실패한 명령이 성공한 것처럼
알려진다. `test_a_recovery_hold_carrying_a_replayed_decision_is_not_called_already_completed`
를 추가했다.

이것이 "정의 사본 + 호출 지점 + **같은 검사의 모든 성분**" 규칙이 겨냥하는 자리다. review 가
지목한 것만 처리했다면 성분 하나가 열린 채 남았다.
