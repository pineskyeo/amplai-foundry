# MGC-012-P5-T041 — limit is an output cap

대상: round 19 `F19-1`(P1), `F19-2`, `R19-1`, `R19-2`. 결정: `D-047`, `D-048`, `D-049`.

## The Root — "읽을 수 없다" 는 SQL 로 판정할 수 없다

`D-048` 은 `unreadable()` 에서 종결 상태만 빼면 `limit` 이 `stranded()` 와 같은 뜻이 된다고
봤다. **틀렸다.** 두 후보 집합이 실제로 다르다.

| 조회 | 후보 집합 |
|---|---|
| `unreadable()` (`D-048` 뒤) | `{pending, leased, retry_wait, recovery_hold, dead_letter}` |
| `_stranded_rows` | `{dead_letter, recovery_hold, retry_wait&소진, leased&소진&만료}` |

그리고 집합을 어떻게 고르든 문제는 남는다 — **손상 여부는 `_view` 를 돌려야 안다.** `SQL
LIMIT` 은 그 판정 **전에** 자르므로 창 안의 읽을 수 있는 row 가 손상 row 를 밀어낸다.

후보 집합을 좁혀서 닫을 수도 없다. 좁히면 `D-047` 이 닫은 round 17 `F17-2`(치우기 실패로
`pending`·`attempts=0` 에 남은 row)가 되살아난다.

## AC-01 — 벽 6종 전수

`D-049` 대로 `LIMIT` 을 SQL 에서 빼고 python 출력 상한으로 옮겼다. 읽을 수 있는 row 는
건너뛰므로 벽이 아무리 두꺼워도 못 민다. `limit` 을 채우면 즉시 멈춘다.

읽을 수 있는 row 150개로 벽을 쌓고 그 뒤에 손상 row 를 두었다. `limit=100` 이다.

| 벽 state | 고침 전 | 고침 후 |
|---|---|---|
| `completed` | HIT | HIT |
| `dead_letter` | **MISS** | HIT |
| `recovery_hold` | **MISS** | HIT |
| `pending` | **MISS** | HIT |
| `retry_wait` | **MISS** | HIT |
| `leased` | **MISS** | HIT |

`completed` 만 막혀 있었고 나머지 다섯이 뚫려 있었다. round 19 는 `leased` 벽을 "CHECK
제약으로 재현 불가" 로 남겼는데, `lease_owner` 와 `lease_expires_at` 을 함께 주면 만들 수
있다 — **여섯 종 전부 실측했다.**

`dead_letter` 와 `recovery_hold` 도 벗어나는 UPDATE·DELETE 가 `src` 에 없어 `completed` 와
똑같이 영구히 쌓인다.

## AC-02 — 큐가 막힌 채로도 보인다

round 19 `F19-1` 재현 B 다. 치우기가 영구히 실패하고 오래된 `dead_letter` 벽 100개가 있다.

```text
claim_next × 3   -> 전부 IngressError(INGRESS_COMMAND_UNREADABLE)
healthy durable  -> ('pending', 0, None)          <- 큐가 실제로 막혔다
unreadable(100)  -> poison 포함                    <- 고침 전에는 빈 목록이었다
```

**`D-047` 의 Consequence("손상 row 는 치우기 실패 경로에서도 operator 에게 보인다")가
처음으로 참이 됐다.** `D-048` 뒤에도 거짓이었다.

## AC-03 — `_dead_letter_unreadable` 에 도달하지 않는 경로 전수

wave 12 는 **하나**로 적었다. 실측은 **둘**이다 (round 19 `F19-2`).

| 경로 | 실측 결과 | `unreadable()` |
|---|---|---|
| `leased`+만료+`attempts >= max` | `('dead_letter', 5, 'INGRESS_LEASE_EXPIRED')` | 나온다 |
| `retry_wait`+`attempts >= max`+`retry_at <= now` | `('dead_letter', 5, None)` | 나온다 |

첫째는 sweep 의 **첫째 UPDATE** 가 `last_error_code` 를 덮은 뒤 둘째 UPDATE 가 옮긴다.
둘째는 첫째 UPDATE 를 거치지 않으므로 **`last_error_code` 를 안 건드린다** — 앞선 값이
남거나 `NULL` 이다. `NULL` 이면 CLI 가 `dead_letter … -` 를 낸다.

**셋 다 사실이다.** `D-045` 의 `INGRESS_COMMAND_UNREADABLE` 은 `_dead_letter_unreadable` 이
치운 경로의 표시이지 "읽을 수 없는 row 의 표시" 가 아니다 — `T042` 가 그 해석을 `D-045` 에
각주로 달았다.

두 docstring(`_sweep_recoverable`, `_dead_letter_unreadable`)에 표로 적었다.

## The Cost — 숨기지 않는다

`D-049` 가 명시적으로 받아들인 대가다. **비용이 `limit` 이 아니라 종결 아닌 row 수에
비례한다.** `D-048` 이 거절 사유로 들었던 바로 그 비용이다.

완화 요소가 둘 있다. `completed` 는 여전히 SQL 에서 빠지고 실무에서 대부분의 row 는 결국
`completed` 가 된다. 그리고 이 조회는 operator 진단 경로이지 worker 의 hot path 가 아니다.
`limit` 을 채우면 즉시 멈추므로 손상이 많을 때는 오히려 빨리 끝난다.

**측정하지 않았다.** round 18 `A18-2`·`A18-3` 이 열어 둔 항목이고 이 wave 의 `non_goals` 다.
