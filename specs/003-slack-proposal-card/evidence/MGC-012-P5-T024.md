# MGC-012-P5-T024 — Normalize Every Store Connection Failure At The Boundary

Wave 8. round 14 `P1-1`. `D-042`.

## AC-01 — Reproduced Before Fixing

`committed_decision` 을 patch 하지 않고 **진짜 `filesystem.py:166` 에서** 예외가 나게 했다.
`LocalFilesystemGuard` 의 probe 를 갈아 끼워 `connect()` 안에서 판정이 뒤집히게 만든다.

착수 전 실측:

```text
before-validate: *** raw GovernanceFilesystemError ***
after-validate : *** raw GovernanceFilesystemError ***
```

`GovernanceFilesystemError` 는 `RuntimeError` 를 상속하지만 `GovernanceStoreError` 의
자식이 아니다 (`filesystem.py:13`, `store.py:18`). 세 지점의 `except` 절은 전부
`(GovernanceStoreError, IngressError, sqlite3.Error)` 라 이 class 를 잡지 못한다.

- `process_next` 의 `claim_next` — `ingress_worker.py:186`
- `_finalize` 의 `_transition` — `:343`
- `_settle_exhausted_retry` 의 `committed_decision()` — `:466-469`

## The Change

`_OPEN_FAILURES = (GovernanceFilesystemError, OSError, sqlite3.Error)` 를 두고 `connect()` 의
**여는 단계**와 `_raw_connection` 의 PRAGMA 를 감싼다.

**호출자를 하나도 안 고쳤다.** `connect()` 호출 지점은 15개 module 62곳이다. 호출자마다
`except` 절에 class 를 더하는 방식이 이 결함의 형태이고, 그 62곳을 세는 일이 다섯 라운드
연속 실패한 작업이다.

세 가지를 지켰다.

- **`yield` 는 두 `try` 밖이다.** 호출자가 던진 예외를 삼키면 안 된다.
- **`Exception` 으로 넓히지 않았다.** `AttributeError`·`TypeError` 는 그대로 나간다.
- **`GovernanceStoreError` 는 다시 감싸이지 않는다.** `RuntimeError` 라 tuple 에 안 걸린다.

원인은 `raise ... from error` 로 `__cause__` 에 보존된다.

### 창을 좁히는 이유 (측정 주의)

`connect()` 는 열 때 `validate()` 를 두 번 부른다. 최종 시도의 호출 순서를 실측했다.

```text
1-2   claim_next
3-4   decision transaction
5-8   committed_decision()  — ingress.get 과 decisions.result_for
9-10  _transition 의 recovery_hold 쓰기
```

처음엔 5 이후를 전부 막았더니 `_transition` 도 실패해 command 가 `leased` 로 남았다.
그것은 store 가 통째로 죽은 다른 경우다. **5 하나만** 막는다 — `before` validate 가 raise
하면 그 `connect()` 는 `after` 를 부르지 않아 호출을 하나만 쓰고, `committed_decision()` 은
첫 읽기에서 멈춘다. 창을 (5,8) 로 잡았을 때 번호가 밀려 `_transition` 까지 막힌 것을 실측으로
확인하고 (5,5) 로 좁혔다.

## AC-06 — `check_startup()` Diagnostics

`check_startup()`(`:234`) 둘 다 **자기 top 에서** `filesystem_guard.validate(self.path)` 를

## AC-09 — What The Normalization Does Not Cover

## Correction — Round 15 `R-1`

**위 sibling census 는 맞았고, 그 전부를 덮기로 한 판단이 틀렸다.**

`_OPEN_FAILURES` 에 `sqlite3.Error` 를 넣어 4·5·7번 형제까지 정규화했다. 그런데
`legacy_*.py` 의 아홉 `try` 가 `sqlite3.Error` 를 잡아 domain error 로 닫고 있었다 —
`legacy_lifecycle:157`, `legacy_migration:823,1069,1114,1169`, `legacy_recovery:206,415`,
`legacy_rollback:180,549`. 정규화가 그 봉쇄를 전부 없앴다. HEAD 대조 실측:

```text
HEAD    : sqlite3.OperationalError | disk I/O error
wave 8  : GovernanceStoreError     | Governance Store connection을 열 수 없습니다: disk I/O error
```

**test 가 하나도 없어서 suite 는 조용했다.** round 15 regression lens 가 AST 로 아홉 handler
를 전수하고 `legacy_recovery.py:206` 을 실행으로 재현해 잡았다.

위 절의 "호출자를 하나도 안 고쳤다" 를 장점으로 적었는데, 아홉 곳에서는 그것이 결함이었다.
고치지 않았기 때문에 그들이 의존하던 예외 class 가 조용히 바뀐 것이다.

`MGC-012-P5-T029` 가 `_OPEN_FAILURES` 를 `(GovernanceFilesystemError, OSError)` 로 좁히고
`_raw_connection` 의 PRAGMA 래핑을 되돌렸다. 4·5·7번 형제는 **의도적으로 정규화하지
않는다** — HEAD 동작이고 아홉 handler 가 그것에 의존한다.

round 14 `P1-1` 이 요구한 것은 `GovernanceFilesystemError` 하나였다. **형제를 전수로 센
것은 옳았고, 센 것을 전부 덮기로 한 것이 틀렸다.** 세는 일과 덮는 일은 다른 판단이다.
