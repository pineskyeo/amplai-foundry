## The Change

`_ExpectedAudit`(`TypedDict`)와 `GovernanceEventService._assert_audit_matches` 하나를 만들고
여덟 지점이 그것을 쓴다. or-chain 은 0개가 됐다 (AST 로 확인).

```python
for field, want in expected.items():
    actual: object = getattr(audit, field)
    if field == "occurred_at":
        actual = cls._timestamp(cast(datetime, actual))
    if actual != want:
        raise GovernanceEventError(code)
```

**`TypedDict` 인 이유.** 평범한 `Mapping[str, object]` 로 받으면 `actor_idd` 같은 오타를
mypy 가 더는 못 잡는다 — or-chain 이 갖고 있던 정적 보호를 잃는 것이다. `TypedDict` 는 key
이름과 값 type 을 호출 지점마다 검사하므로 그 보호를 유지하면서 "빠진 필드가 mapping 에서
눈에 보인다" 를 얻는다.

**변환은 하나뿐이다.** `occurred_at` 만 view(`datetime`)와 row(문자열)의 형이 다르다. 그
변환을 helper 안 한 곳에 두고 나머지는 `getattr` 그대로다.

**거부 조건은 안 바뀐다.** or-chain 은 첫 불일치에서 멈췄고 loop 도 그렇다. 같은 입력에 같은
code 를 낸다.

## A Measurement I Got Wrong, And The Correction

after-sweep 을 처음 돌렸을 때 72 key 중 42개가 SURVIVED 로 나왔다. **그 값은 틀렸다.
결과가 아니라 내 축약의 결함이다.**

축약은 이랬다 — helper 의 비교 한 줄을 끄면 여덟 지점이 전부 raise 를 멈추므로, 그때
실패하는 test 집합이 "key 하나를 지웠을 때 실패할 수 있는 test" 의 상한이다. 이 논증은
**실행으로 알아채는 test 에만 성립한다.** key 를 지우는 mutation 은 `events.py` 의 source 를
읽는 AST test 도 알아채는데, 그 test 는 비교를 꺼도 실패하지 않으므로 후보 집합에 안 들어갔다.
후보에 없으니 돌지 않았고, 돌지 않았으니 SURVIVED 로 셌다.

baseline sweep 의 축약은 같은 결함이 없다 — 그때는 or-chain 을 지우는 mutation 뿐이었고
source 를 읽는 test 가 존재하지 않았다. 그래서 표본 3건 전 suite 검증도 통과했다.

후보 집합에 AST test 둘을 넣어 다시 측정했다. 아래 AC-05 표의 값이 그 재측정값이다.
**실행만으로 잡히는 것은 30/72** 였다 (기준선 10 에서 올랐다). 나머지는 AST test 가 덮는다.

## AC-07 — The Field Asymmetry, Answered

### `policy_snapshot_id` — 3/8 만 본다. **의도다.**

보는 셋은 기대값을 durable data 로 **복원할 수 있다**.

| block | 기대값 |
|---|---|
| L1480 | `_digest(f"{mapping_policy_version}:{validation_policy_ref}")` — payload 에서 나온다 |
| L1557 | `_digest(b"legacy-approval-human-review:v1")` — 고정 문자열 |
| L1711 | `_digest(b"legacy-forward-recovery:v1")` — 고정 문자열 |

안 보는 다섯은 그 값이 `_policy_snapshot(authority)`(`events.py:2765-2774`)로 쓰인다 —
**쓰기 시점 actor 의 permission 집합의 digest** 다. `reconcile_connection` 은 durable row 만
읽으므로 그 permission 집합을 복원할 수 없다. **대조할 기대값이 존재하지 않는다.**

### `proposal_ref` — 2/8 만 본다. **절반은 의도, 절반은 구멍이다.**

| block | audit 조회 방식 | `proposal_ref` 대조 | 판정 |
|---|---|---|---|
| L1254 | `WHERE command_id = ?` | ✓ | 필요하고 있다 |
| L1711 | `WHERE command_id = ?` | ✓ | 필요하고 있다 |
| L1795 | `WHERE command_id = ? AND project_namespace = ? AND project_id = ? AND proposal_id = ?` | ✗ | **query 가 이미 묶는다. 의도** |
| L1875 | 같은 4-column query | ✗ | 의도 |
| L1480 | `WHERE command_id = ?` | ✗ | **구멍** |
| L1557 | `WHERE command_id = ?` | ✗ | **구멍** |
| L1959 | `WHERE command_id = ?` | ✗ | **구멍** |
| L2113 | `WHERE command_id = ?` | ✗ | **구멍** |

`governance_audit_events` 의 `command_id` 에는 UNIQUE 제약이 없다
(`migrations.py:459-497`). `len(audits) != 1` 이 그 command_id 의 audit row 가 하나임은
보장하지만, **그 row 가 어느 proposal 을 가리키는지는 아무것도 묶지 않는다.** 네 지점에서
audit row 가 다른 proposal 을 가리켜도 통과한다.

**고치지 않았다.** 감사 대조에 필드를 더하는 것은 governed 동작 변경이고 manifest 의
`scope.exclude` 가 "누락이면 finding 으로 기록하고 별도 task 로 낸다" 로 못박았다.

→ **Finding T023-F1**: `LEGACY_MIGRATION`, `LEGACY_APPROVAL_REVIEW`, `APPLY_JOB`,
`PUBLISH_RESOLUTION` 네 감사 대조가 audit row 의 proposal 동일성을 확인하지 않는다. query 도
안 묶는다. Decision 이 필요하다 — `expected` mapping 에 `proposal_ref` 를 더할지, query 에
proposal 3-column 을 더할지(L1795·L1875 방식), 아니면 현 상태가 의도인지.

이제 mapping 이 나란히 놓여 이 비대칭이 코드에서 바로 보인다. or-chain 이었을 때는 여덟 곳을
펼쳐 세야 알 수 있었다.
