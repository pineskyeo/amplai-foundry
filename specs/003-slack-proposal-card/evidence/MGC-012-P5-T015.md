# MGC-012-P5-T015 — Sanitize Every Slack Transport Failure At The Shared Exit

date: 2026-08-17
wave: 7 (workstream numbering)
closes: round 13 `F-1` (P1), `F-2` (Blocking-P2), `PBC-1`, `PBC-2`

## What Was Wrong

`post_message` 와 `post_ephemeral` 만 `_sanitized_transport_error()` 를 불렀다.
`read_history` 와 `delete_message` 는 `_call` 을 맨몸으로 불렀다. `_fail()` 과
`_fail_http()` 가 둘 다 `... from error` 로 올리므로 `__cause__` 에 원본 urllib 예외가
붙고, 그 traceback frame 이 `Authorization: Bearer <token>` 을 든 header dict 와 raw
request byte 를 들고 있다.

`_send` 의 `finally` 는 **자기 frame 의 local 만** 비운다. `__cause__` chain 에는 닿지
못한다.

이 측정이 raw byte(`msg`, `data`)까지 보기 때문이고, header dict 만 보면 절반을 놓친다.

## AC-08 — Where `SlackTransportError` Comes From, And How It Leaves

| 발생 함수 | chain | `_send` 안에서 잡는 arm | 고치기 전 sanitize | 고친 뒤 |
|---|---|---|---|---|
| `_fail` (`:795`) | `from error` 있음 | `except Exception` (`:572`) | 호출자 넷 중 둘 | `_call` 이 전부 |
| `_fail_http` (`:756`) | `from error` 있음 | `except HTTPError` (`:570`) | 호출자 넷 중 둘 | `_call` 이 전부 |
| `_decode` (`:719`) | 없음 | try 본문 → `except SlackTransportError: raise` (`:567`) | 해당 없음 | `_call` 이 전부 |

세 경로가 전부 `_send` 밖으로 `SlackTransportError` 로 나가고, 이제 그 셋이 `_call` 의
`except SlackTransportError` 하나를 지난다.

## The Fix

기존 `_call` 본문을 `_send` 로 옮기고, 새 `_call` 이 그것을 감싼다.

```python
def _call(self, method, build_body, content_type):
    try:
        return self._send(method, build_body, content_type)
    except SlackTransportError as error:
        raise _sanitized_transport_error(error) from None
```

**호출자마다 두지 않는다.** wave 6 이 `BaseException` guard 에 대해 이미 옳은 방향을
택했고(`_call` 안에 두어 사본을 없앴다), `SlackTransportError` 도 같은 통로로 보낸다.

호출자 넷의 중복 sanitize 호출은 걷어냈다. `post_message` 와 `post_ephemeral` 이
`except SlackTransportError` 를 여전히 잡는 것은 sanitize 때문이 아니라 `payload`,
`marker`, `text` local 을 비우기 위해서다. 주석에 그 이유를 적었다.

### 형제 위치 하나를 더 줄였다

`post_message` 의 `except BaseException` arm 에도 `_clear_exception_frames(error)` 사본이
있었다. 그것을 남겨두면 **`_send` 안의 guard 를 가린다** — 아래 AC-04 실험이 처음에
`post_message` 만 통과시켜서 드러났다. 제거했다.

`_clear_exception_frames` **호출** 지점은 이제 `slack_http.py` 안에 둘이다
(`_send` 의 BaseException arm, `_sanitized_transport_error`). 둘 다 아래 mutation 으로
고정된다.

`_clear_exception_frames` **정의** 사본은 저장소에 넷이다 — `slack_http.py`,
`decisions.py:775`, `slack_projection.py:1127`, `slack_cards.py:327`. `D-038` 항목 4 가
기록한 알려진 한계이고 이 task 의 `allowed_paths` 밖이다. **닫지 않았다.**

### AC-04 는 처음에 살아남았다

첫 실행에서 `_send` 의 guard 를 지워도 242건이 전부 통과했다. **stop rule 대로 코드보다
test 를 먼저 의심했고, 원인이 둘이었다.**

1. **올라가는 예외로는 이 guard 를 볼 수 없다.** `raise_sanitized_interruption` 이
   `from None` 이라 원본에 닿지 않는다. guard 가 지키는 것은 **원본 예외 객체를 따로 들고
   있는 쪽**이다. 미리 만든 예외를 재사용하거나 예외를 캐시하는 library 가 그런 참조를
   만든다.
2. **fake opener 가 한 겹이라 `finally` 가 이미 다 막았다.** 실제 urllib 은
   `open` → `_open` → `http_open` → `do_open` 을 지나며 그 frame 들이 `Request` 를 든 채
   죽는다. `_send` 의 `finally` 는 자기 frame 만 비우므로 **더 깊은 frame** 이 남고,
   그것을 비우는 것이 이 guard 다. fixture 가 한 겹이면 그 깊이가 존재하지 않는다.

`_OpenerRaising` 에 `_deliver` 를 한 겹 두어 실제 chain 의 깊이를 흉내내고, 원본 예외
객체를 검사하도록 test 를 썼다. guard 를 지운 상태에서 실측한 값이다.

```
보관된 원본으로 도달 : [('open', 'request'), ('_deliver', 'request')]
```

## Tests That Passed By Construction — Fixed

### PBC-1 — fixture 가 검사 대상을 먼저 지웠다

`_OpenerRaising.open` 이 `del request, timeout` 을 했다. 그 `request` 가 guard 가
지우려는 대상 **자체**다. 지웠다. 이제 참조를 남기고 `_deliver` 로 한 겹 더 내려간다.

### PBC-2 — 실제 누출 arm 을 한 번도 안 탔다

기존 token 누출 test 는 `_NotAnException` 만 주입해 `except BaseException` arm 만 탔다.
누출은 `except Exception` 과 `except HTTPError` 에서 났다. 세 arm 을 각각 덮는 test 를
추가했다.

| arm | test |
|---|---|
| `except urllib.error.HTTPError` | `..._when_slack_answers_with_an_http_error` |
| `except Exception` | `..._when_the_connection_is_refused` |
| `except BaseException` | `..._keeps_no_bot_token_in_the_frames_below_the_transport` |
| try 본문 (`_decode`) | `..._when_slack_answers_ok_false` |

### 측정 함수도 고쳤다

`_bearer_holding_frames` 가 header dict 만 봤다. raw byte(`msg`, `data`)도 보게 넓혔다.
그리고 이 test 모듈 자신의 frame 을 기본으로 제외한다 — 측정 도구가 들고 있는 token 을
누출로 세면 어떤 구현이든 실패한다.
