# Feature Specification: AMPLAI Loop Runtime Adoption

**Feature Branch**: `004-amplai-loop-runtime`

**Created**: 2026-08-19

**Status**: Approved for planning

**Input**: `D-046` 과 `docs/workstreams/amplai-loop-runtime-adoption/FACTS.md`. cortex main
`3a3eb46b` 의 AMPLAI Loop Runtime V2.1 을 이 저장소로 이식한다.

## Context

이 저장소의 개발 절차는 사람이 고정 순서를 손으로 태운다 — `/speckit-specify` → `clarify` →
`plan` → `/taskify` → validator → `tasks.md` 생성 → `/speckit-analyze` → `/speckit-implement`
→ subagent review 3인. 그 순서는 `CLAUDE.md` 의 Pre-Implement Procedure 가 규칙으로 못박았다.

2026-08-18~19 세션이 그 대가를 실측으로 보여줬다. wave 8 → round 15 → wave 9 → round 16 →
wave 10 을 손으로 돌리는 동안 수치를 여섯 라운드 연속 틀렸고, 수정이 새 blocker 를 만들었으며
(round 16 blocker 9건 중 다수가 직전 wave 의 산물), reviewer 가 세 번 세션 한도로 죽어 판정
자체를 잃었다.

cortex 는 같은 문제를 loop runtime 으로 풀었다. 공개 명령을 `/work` 와 `/design` 둘로 줄이고
나머지를 controller 가 고르는 internal capability 로 내렸다. 완료는 말이 아니라 executable
evidence 로 판정한다.

이 feature 는 그 runtime 을 가져와 **이 저장소의 개발 자체에** 쓴다. 제품(Knowledge Vault,
Proposal, governance store)은 바뀌지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Start Work Without Choosing A Procedure (Priority: P1)

개발자가 목표 하나만 말하면 나머지 절차는 runtime 이 고른다. 어떤 단계가 필요한지, 어떤
순서인지 사람이 정하지 않는다.

**Why this priority**: 이것이 이 feature 의 존재 이유다. 순서를 사람이 태우는 비용이
측정됐고, 나머지 story 는 이 story 가 성립해야 의미가 있다.

**Independent Test**: 서로 다른 성격의 목표 셋(문구 수정, 회귀 버그, 새 기능)을 같은 진입점
하나로 넣고, 각각 다른 경로를 타면서 완료까지 가는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 개발자가 목표 문장 하나를 준다, **When** 작업을 시작한다, **Then** runtime 이
   위험도와 성격을 분류하고 필요한 단계만 실행하며, 개발자는 단계 이름을 하나도 부르지 않는다.
2. **Given** 사소한 문구 수정, **When** 같은 진입점으로 넣는다, **Then** 무거운 설계 단계를
   건너뛰고 검증만 거쳐 끝난다.
3. **Given** 도메인 지식이 필요한 작업, **When** 같은 진입점으로 넣는다, **Then** 지식이
   준비되기 전에는 구현을 시작하지 않는다.
4. **Given** 중단된 작업, **When** 같은 진입점에 그 작업을 다시 준다, **Then** 처음부터
   다시 하지 않고 남은 지점부터 재개한다.

---

### User Story 2 - Completion Judged By Evidence, Not By Claim (Priority: P1)

완료 판정이 실행 가능한 증거로만 이뤄진다. 작업자의 자기평가는 판정 근거가 되지 않는다.

**Why this priority**: 여섯 라운드 연속 수치 오류가 자기평가를 근거로 쓴 결과다. Story 1 과
같은 우선순위인 이유는 loop 가 돌아도 판정이 무르면 같은 실패가 반복되기 때문이다.

**Independent Test**: 통과하지 않은 검증을 통과했다고 주장하는 상태를 만들고, 완료가 거부되는지
확인한다.

**Acceptance Scenarios**:

1. **Given** 검증이 실패한 작업, **When** 완료를 선언하려 한다, **Then** 거부되고 어떤 검증이
   왜 실패했는지 남는다.
2. **Given** 검증을 실행할 수 없는 환경, **When** 완료를 선언하려 한다, **Then** 실행 불가를
   통과로 표현하지 않는다.
3. **Given** 완료된 작업, **When** 기록을 읽는다, **Then** 무엇을 근거로 통과했는지 재구성할
   수 있다.

---

### User Story 3 - Resume After An Interrupted Session (Priority: P2)

세션이 끊겨도 다음 세션이 기록만 읽고 이어받는다. 사람이 상황을 다시 설명하지 않는다.

**Why this priority**: 이번 세션에서 reviewer 가 세 번 죽어 판정을 잃었다. 복구 가능성이
없으면 긴 작업이 매번 처음으로 돌아간다.

**Independent Test**: 작업 중간에 세션을 끊고, 새 세션이 기록만으로 같은 지점에서 이어가는지
확인한다.

**Acceptance Scenarios**:

1. **Given** 구현 도중 중단된 작업, **When** 새 세션이 시작한다, **Then** 어디까지 됐고 다음이
   무엇인지 기록에서 읽어낸다.
2. **Given** 이미 완료된 작업, **When** 같은 목표를 다시 준다, **Then** 증거를 확인하고 다시
   실행하지 않는다.

---

### User Story 4 - Documentation Stays True Before Review (Priority: P3)

리뷰어가 볼 때 코드와 문서가 이미 맞아 있다. 문서가 낡은 채로 완료되지 않는다.

**Why this priority**: 이번 세션에서 문서의 거짓 진술(수치, 존재하지 않는 진입점 주장)이
blocker 로 반복해 나왔다. 다만 앞의 셋이 없으면 이것만으로는 실패를 못 막는다.

**Independent Test**: 코드를 바꾸고 관련 문서를 그대로 둔 채 완료를 시도해 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 코드 변경이 문서와 어긋난다, **When** 리뷰 단계에 들어가려 한다, **Then** 문서
   불일치가 먼저 드러난다.
2. **Given** 문서 정리가 필요한 상태, **When** 정리를 제안한다, **Then** 보호 대상 경로는
   제안까지만 하고 자동으로 지우지 않는다.

### Edge Cases

- 목표가 모호해 분류가 안 된다: 사람에게 묻고 멈춘다. 추정으로 분류하지 않는다.
- 지식이 서로 충돌한다: 임의로 하나를 고르지 않고 충돌로 표면화한다.
- 검증 환경이 없다: 통과로 표현하지 않는다. 실행 불가로 남긴다.
- 작업 범위가 도중에 커진다: 조용히 넓히지 않고 기록한다.
- 보호 대상(공식 지식)을 정리 후보로 잡는다: 제안까지만 하고 사람 승인 없이는 손대지 않는다.
- 이 저장소에 이미 있는 절차 문서와 새 규칙이 어긋난다: 한쪽이 이긴다는 것이 명시돼 있다.
- 이식 대상 도구가 이 저장소에서 실행되지 않는다: 이식을 중단하고 이유를 남긴다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 개발 작업의 사용자 진입점은 **정확히 둘**이어야 한다 — 목표를 끝까지 수행하는
  것 하나, 구현 없이 요구·설계·결정만 확정하는 것 하나.
- **FR-002**: 기존 개별 단계(요구 작성, 모호성 해소, 설계, 작업 분해, 정합성 점검, 구현,
  수렴, 리뷰, 디버그)는 사용자가 직접 호출하는 대상에서 내려가고 controller 가 선택해야 한다.
- **FR-003**: controller 는 작업의 위험도와 성격을 분류하고, 그 결과에 따라 **필요한 단계만**
  실행해야 한다.
- **FR-004**: 도메인 지식이 필요한 작업은 지식 준비 상태가 확인되기 전에 구현을 시작하지
  않아야 한다.
- **FR-005**: 완료 판정은 실행 가능한 검증의 결과로만 이뤄져야 하며, 작업자의 자기평가를
  통과 근거로 쓰지 않아야 한다.
- **FR-006**: 검증은 이름 있는 묶음으로 실행할 수 있어야 하고, 이 저장소가 이미 가진 검증
  항목 전부가 그 묶음에 포함돼야 한다.
- **FR-007**: 검증을 실행할 수 없는 상태를 통과로 표현하지 않아야 한다.
- **FR-008**: 작업의 진행 기록은 다음 세션이 그것만 읽고 재개할 수 있을 만큼 남아야 한다.
- **FR-009**: 이미 완료된 작업은 증거를 확인한 뒤 다시 실행하지 않아야 한다.
- **FR-010**: 구현 후 독립 리뷰는 유지돼야 하며, 차단 등급 지적이 하나라도 있으면 완료로
  판정하지 않아야 한다.
- **FR-011**: 문서 최신성 확인은 리뷰 **앞**에, 저장소 정리는 리뷰 **뒤**에 위치해야 한다.
- **FR-012**: 저장소 정리는 기본이 제안이어야 하며, 명백한 임시 산출물 외에는 자동으로
  삭제하지 않아야 한다.
- **FR-013**: 공식 지식 저장 경로는 사람 승인 없이 변경되지 않는 보호 대상으로 지정돼야 한다.
- **FR-014**: 위험한 행위(공개 계약 변경, 파괴적 이행, 배포, 원격 반영)는 차단되거나 명시적
  관문을 거쳐야 한다.
- **FR-015**: 이 저장소의 개발 규칙 문서는 어느 문서가 실질 규칙이고 어느 것이 도구별 보조
  지침인지 명확해야 하며, 둘이 어긋날 때 무엇이 이기는지 적혀 있어야 한다.
- **FR-016**: 이식 대상에서 제외한 영역(의미망·추론 계층)은 문서에 제외 사실과 이유가
  남아야 한다.
- **FR-017**: 이식 후에도 이 저장소의 제품 동작은 바뀌지 않아야 한다.
- **FR-018**: 기존에 흩어져 있던 개발 능력 정의의 위치가 하나로 정리돼야 하며, 중복 정의가
  남지 않아야 한다.
- **FR-019**: 이식된 runtime 자체가 이 저장소의 검증 묶음으로 검사돼야 한다.

### Key Entities

- **Work**: 하나의 목표와 그 수행 전체. 분류 결과, 계약, 진행 상태, 증거를 갖는다.
- **Work Contract**: 그 Work 가 무엇을 만족해야 끝나는지의 선언. 구현 전에 정해진다.
- **Knowledge Readiness**: 구현을 시작해도 되는지의 판정. 준비·우회·조사필요·차단 중 하나다.
- **Verifier Profile**: 이름 붙은 검증 묶음. 각 검증은 실행 가능한 명령과 차단 여부를 갖는다.
- **Evidence Trace**: 무엇을 근거로 어떤 판정에 이르렀는지의 시간순 기록.
- **Handoff**: 다음 세션이 이어받는 데 필요한 최소 상태.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 개발자가 작업을 시작할 때 부르는 명령이 **둘**이다. 그 외 단계 이름을 부르지
  않고 대표 작업 세 종류를 완료까지 수행할 수 있다.
- **SC-002**: 완료로 판정된 작업 100%가 실행된 검증 결과를 근거로 갖는다. 실행되지 않은
  검증을 근거로 삼은 완료가 0건이다.
- **SC-003**: 이 저장소가 기존에 갖고 있던 검증 항목 전부가 새 검증 묶음에서 실행되고, 이식
  전후로 그 결과가 같다.
- **SC-004**: 중단된 작업을 새 세션이 기록만 읽고 재개해 완료까지 간다. 사람이 상황을 다시
  설명하지 않는다.
- **SC-005**: 공식 지식 경로에 대한 자동 변경이 0건이다.
- **SC-006**: 이식 전후로 제품 동작을 확인하는 기존 검증이 모두 같은 결과를 낸다.
- **SC-007**: 개발 규칙을 처음 읽는 사람이 어느 문서가 실질 규칙인지 한 번에 찾는다.
- **SC-008**: runtime 자체를 검사하는 검증이 존재하고 통과한다.

## Assumptions

- 이식 대상은 cortex main `3a3eb46b` 시점의 V2.1 이다. 그 이후 변경은 범위 밖이다.
- 의미망 계층(온톨로지, 형상 검증, 읽기 전용 도구 서버)은 가져오지 않는다. 이 저장소에는
  그 기반이 없고 Knowledge Vault 와 Proposal 모델이 그 자리를 대신한다.
- 구현 후 독립 리뷰 3인 체제는 유지한다. `D-033` 이 그것을 승인 절차가 아닌 검증으로 남겼고
  `D-046` 이 그 판단을 이어받는다.
- 이 저장소의 제품 코드(`src/amplai_foundry/`)는 이 feature 로 바뀌지 않는다. 바뀌는 것은
  개발 절차와 그것을 지탱하는 저장소 상단 구조다.
- 진행 중이던 `MGC-012 Package 5` 는 round 17 이 열린 채로 남는다. 사용자가 이식을 먼저
  하기로 정했다.
- 이식된 도구는 외부 의존성을 새로 요구하지 않는다 — 실측으로 표준 라이브러리만 쓴다.
- Python 실행 환경은 이 저장소의 기존 환경을 그대로 쓴다.
